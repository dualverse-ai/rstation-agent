# Agent pool dashboard

A private, read-only view of researcher activity. It listens only on 127.0.0.1:8911 and has no worker-control endpoints. It uses existing SSH access to H4, H6 and H7 and unauthenticated public rStation profile APIs. No H1 access or provider request is needed.

Run from the launcher directory:

```
python3 fleet_dashboard.py --config /PRIVATE/PATH/fleet.json --data /PRIVATE/PATH/fleet-history
```

The private config contains `hosts` (host alias to a list of existing toolkit directories) and optional `accounts` (host/run/worker to a public handle and verified stop reason). A stopped slot is intentional only with explicit owner evidence, never from a PAUSE/STOP marker alone. Do not put keys in this config. The toolkit reads account files locally on each host only to extract a public handle; it never exports their other fields. Errors are allowlisted categories and HTTP status numbers, never raw logs.

Host collection runs every two minutes; public account data refreshes separately, at most hourly per account. The page refreshes every 30 seconds. Missing or older-than-five-minute host evidence makes an active worker yellow, or red once its response clock reaches six hours. A process being alive does not establish health. Seven-day history and 24-hour observed totals start with this collector; gaps remain gaps. The SQLite history retains eight days. Keep the data directory private and outside Git.

Field sources:

- Run/model/route/state: run.json and runtime state; per-worker effective model overrides are included.
- Real response/completed tool: native activity timestamps recorded by the launcher.
- GPU: live owned GPU helper/job receipts. Job presence alone never establishes progress. An unfinished native tool, a verified descendant GPU job and an open workspace log with increasing training-step counters across two samples establish advancing work. Below the six-hour response threshold, a running worker stays Working while that same foreground job has advanced within ten minutes; frozen counters, vanished jobs and stale host samples lose that evidence. Native response age and provider health remain independent. The collector inspects descriptor links as the workspace account and exports no log paths or contents. Disk: most recent recorded workspace size and allowance.
- Owner messages: queue status and recorded owner receipt time; message bodies are excluded.
- Handle: known account-file fields; registration and published-paper counts: public profile APIs.
- Last public activity: public posts/comments/papers. This is NOT the complete interaction time. Full platform interaction and local platform receipt remain Unknown where no trustworthy structured source is available.
- Intentional stop: explicit owner-message mapping. Unverified stopped slots remain visible. Retired slots are not inferred merely from a successor name.

The first version enumerates run.json in configured toolkit roots. Removed/archived rosters without a remaining run.json cannot be reconstructed from this view. Hosts outside the configured installations, complete interaction history, reflection due state and native session/result-file details need additional collection. Profile failures leave unknown or visibly aged account evidence. No page contains keys, transcripts or operator-message text.

Tests: `python -m pytest tests/test_fleet_dashboard.py tests/test_fleet_attention.py tests/test_fleet_gpu_progress.py` and `node tests/test_fleet_ui.js`. Includes health from work rather than process presence, stale evidence, history gaps, concurrent SQLite reads/writes, secret exclusion, account parsing, independent profile fetch and read-only loopback HTTP access.

The page uses the live GPU Pool dashboard (http://localhost:8910/) as its visual reference: the same typography, light/dark colours, compact header and bordered cards. The default table shows health, problem, worker, model, last response and a plain-language reason. Select a worker for the other measurements and history. Retired slots have a separate count and table, revealed by the checkbox. Search filters both active rows and their pool/family counts. Green + yellow + red always equals the displayed active-worker total; retired workers are outside that total. Theme selection is saved only in the browser.

Provider summary tiles show Gemini, Claude and Codex separately. Responding means at least one non-retired worker produced a real model response within ten minutes, using host evidence no older than five minutes. A completed tool or live process alone does not establish provider response. A family can be responding while some of its workers need attention; both counts are shown. Missing or stale evidence is Unknown, not a provider failure. The worker table puts workers needing attention first. The favicon and header share a navy, teal and gold grid mark.

API key health appears above the worker table, grouped into Gemini, Claude and Codex, with primary first and backups in numeric priority order. A key used by more than one family appears in each relevant group. It adapts the named provider rows and availability-history idea from https://status.ikuncode.cc/, read on 27 November 2026. Unlike that service, it performs no paid probes and claims no uptime percentage: it uses identified worker responses, HTTP/provider errors and an observed 90-minute history, with gaps. Internal route priority determines row order; endpoint display removes URL credentials, queries and arbitrary path segments. Keys are fingerprinted on the host and never exported or logged. The collector reads only identified rStation process/provider fields and rStation-purpose configuration. When process metadata is inaccessible, a saved matching provider-pool fingerprint is required before attributing a worker result to a configured key. Unverified connections are counted explicitly, and unobserved or stale keys remain Unknown.

Key identities remain internal. The key name shown on the page is exclusively the canonical `provider_tokengroup_suffix` name, with a numeric suffix when needed. Fingerprints, old variable names, route-slot labels and provider-interface token names are not displayed as key names. Missing or conflicting canonical names show an explicit unavailable/conflict state.

Internal key names are read from `.provider-labels.json` beside each host toolkit: `{"labels":{"<key identity hash>":"ikun_gemini_rstation"}}`. Populate names only after matching the exact key and endpoint fingerprint to the purpose-specific credential inventory. This file contains no credentials, is ignored by Git and is reread on each collection; changing a label does not reload a worker or alter provider selection. The Name column shows only the canonical name. Primary/backup priority still determines row order. Provider URL and provider-interface token name belong in the private bin inventory maintained by the operator, separate from the display name.

Collector route selection mirrors the deployed H4/H6/H7 launcher: only `RSTATION_WORKER_*` fields define controller pools, including backups and proxies. Generic CLI variables are read only from an identified native process as evidence of its selected connection. Missing or empty dedicated fields never fall back to generic credentials. An active provider registry is selected by the worker’s saved revision; mismatched revisions or pool fingerprints leave attribution unverified. Successful complete collections replace each host’s current key inventory while preserving sampled history.

The middle portion names the provider’s actual token group in English, not a model-family guess (for example `ikun_cc_reverse_rstation`, `hapi_gemini_antigravity_rstation` and `rightcode_gemini_highquality_personal`). The operator maintains the verified translation in the canonical mapping; raw group spelling and provider-interface labels remain private bin inventory metadata. Canonicalization case-folds Latin letters and replaces spaces and hyphens with underscores. The entire name is validated, excluding empty components, controls and markup.

Every active worker has one `health` status: `working` (green), `transient_error` (yellow), or `needs_attention` (red). Red takes priority at exactly six hours since the latest real model response, regardless of process state, tools or GPU progress. Until the first response, the clock starts at the first recorded observation. The clock persists through worker and dashboard restarts. Only a real model response resets it. Below that threshold, blocked, retrying, paused, stopped, stale and otherwise nonworking slots are yellow. Green requires a running/continuing state, fresh host evidence and a recent response/completed tool or verified advancing foreground experiment. Actual process state and response age remain visible.

Explicitly retired workers have `health=intentional` and appear separately. Pool and family counts, row badges, filtered worker lists and the hook all derive from `health`. Provider/key availability is separate evidence and does not override a worker status. Missing host data never hides a worker or suppresses an already-due alert.

Each `/api/snapshot` worker includes `needs_attention` (exactly `health == "needs_attention"`), `attention_known`, `attention_since`, `attention_due_at` and `attention_threshold_seconds` (21600). `attention_known` means the response/first-observation clock is known, independently of host freshness. Consumers can retain their check of both booleans. Top-level and family `need_attention` equal `counts.needs_attention`; `active_total` equals the sum of the three active status counts. On a failed page refresh, last recorded process states remain visible, active rows turn yellow or overdue red, and the response clocks continue.

Ongoing native Claude `system/api_retry` events make a running worker yellow even when its preceding response is recent. Only the current live launch is inspected; a later real assistant response or successful result clears the retry. Retry evidence expires after five minutes, and repeated collection or unrelated transcript writes do not renew it. Older launches, pre-launch/future timestamps and incomplete records cannot establish a retry. The six-hour response rule still takes precedence. Only an HTTP status and observation time leave the collector; error text stays private.
